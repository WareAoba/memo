# 앱 동작 점검 — 2026-09-26

현재 작업 트리를 대상으로 프런트와 백엔드를 검토한 시점 기록이다. 구현 상태의 기준은 [STATUS](STATUS.md), 요구 계약은 [SPEC](../SPEC.md)이다. 최초 점검에서는 제품 코드를 수정하지 않았다.

후속 수정: 아래 세 결함을 수정하고 Today·일정 API·푸시 작업자 회귀 테스트를 추가했다. 아래 재현 결과는 수정 전 기록이다.

## 확인된 결함

### 1. [P1] 자정 이후 메모 저장이 열린 실행 초안을 없앤다

위치: [Today.tsx](../frontend/src/features/workspace/Today.tsx), `refresh`의 편집 보호 조건(55–70행)과 `changed`(79–81행).

재현:

1. Today에서 그날 끝나는 일정의 실행 태스크 팝업을 연다.
2. 실행 항목에 값을 입력하되 항목 저장은 하지 않는다.
3. 자정을 지나 Today의 날짜가 다음 날로 바뀐다. 이때까지는 팝업과 초안이 유지된다.
4. 별도의 실행 메모를 자동 저장한다. 성공한 PATCH가 `schedules-changed` 이벤트를 발생시킨다.
5. 다음 포커스 복귀 또는 30초 조회 주기가 실행된다.

실제 결과: 다음 날 일정으로 목록을 교체하면서 이전 날 카드와 실행 팝업이 언마운트된다. 저장하지 않은 실행 항목이 사라진다. 재현 테스트에서 입력 요소가 `null`이 됐다.

원인: `requested=true`가 되면 `editing` 보호를 우회하고 `getDaySchedules(today)` 결과로 날짜까지 교체한다. `displayDate`가 이전 날짜를 붙잡고 있어도 결과 자체가 교체되므로 보호되지 않는다.

수정 방향: 편집 중인 날짜가 현재 날짜와 다르면 변경 이벤트도 날짜 교체를 지연해야 한다. 필요한 갱신은 편집 중인 날짜에 적용하고, 편집 종료 후 새 날짜를 조회한다.

추가 재현 테스트: `audit preserves an unsaved execution draft after midnight and a memo save event`. 최신 제품 코드와 번역 파일로 다시 실행해 동일 실패를 확인했다.

### 2. [P2] 프리셋 승격 후 기존 완료 태스크의 메모·이름 저장이 막힌다

위치: [execution.rs](../backend/src/services/execution.rs), `task`의 필수 항목 검사(136–137행). 연관 경로: [unmanaged_presets.rs](../backend/src/services/unmanaged_presets.rs)의 `promote`.

재현:

1. 이름 직접 입력으로 세부 항목이 없는 태스크를 일정에 만들고 완료한다.
2. 같은 이름의 정식 태스크 프리셋을 생성하면서 기본값이 비어 있는 필수 항목을 추가한다.
3. 기존 완료 태스크의 `execution_notes`만 PATCH한다.

실제 결과: `409 REQUIREMENTS_INCOMPLETE`. 이름만 수정해도 같은 검사에 걸린다.

원인: 승격은 명세에 따라 기존 완료 상태를 유지하면서 새 필수 항목을 추가한다. 이후 메모만 수정해도 `status`가 기존 `completed`로 해석되어 새로운 필수 항목 검사를 실행한다. 완료 기록의 메모를 수정하려면 완료를 취소하거나 과거 기록에 새 값을 입력해야 한다.

수정 방향: 완료로 전환하는 요청의 검증과 기존 완료 기록의 메타데이터 편집을 구분한다. 승격 후에도 실행값과 완료 상태를 보존하면서 메모·이름을 수정할 수 있어야 한다.

추가 재현 테스트: `audit_completed_promoted_task_allows_memo_edit`. 예상 HTTP 200, 실제 HTTP 409.

### 3. [P2] 발송 전 취소된 푸시 작업이 일정 재개 후 복구되지 않는다

위치: [reminder_worker.rs](../backend/src/reminder_worker.rs), `claim`의 취소·등록·선택 쿼리(14–18행).

재현:

1. 알림 시각이 도래했지만 시작 전인 일정에 아직 발송되지 않은 `pending` 또는 `sending` 전달 작업이 존재한다.
2. 일정을 완료하거나 취소하여 작업이 `cancelled`로 바뀐다.
3. 시작 전에 완료를 취소하거나 일정을 재개한다. 리마인드 설정과 버전은 그대로다.
4. 스케줄러가 다시 작업을 조회한다.

실제 결과: 발송 대상이 0건이고 전달 행은 계속 `cancelled`로 남는다. 해당 기기는 시작 전까지 알림을 받지 못한다.

원인: `(subscription_id, schedule_id, reminder_version)` 유일 조건 때문에 `INSERT OR IGNORE`가 기존 취소 행을 재생성하지 못한다. 다음 조회도 `pending`과 만료된 `sending`만 선택한다.

수정 방향: 같은 버전의 일정이 다시 활성 상태가 되면 미발송 취소 작업을 재개할 수 있어야 한다. 이미 발송했거나 인앱 수신 처리한 작업은 중복 발송하지 않아야 한다.

추가 재현 테스트: `audit_reopening_before_first_delivery_restores_pending_reminder`. 예상 claim 1건, 실제 0건; DB 상태 `cancelled`.

## 점검 범위와 방법

- 프런트: 계정 부트스트랩, 라우팅·중첩 팝업, 프리셋·워크 기본 태스크, 일정 작성·수정, 실행값·완료·메모, Today의 갱신과 날짜 전환, 캘린더·검색, 사진, 설정·초기화, 인앱 알림·서비스 워커.
- 백엔드: 인증 컨텍스트와 소유자 범위, CRUD·입력 검증, transaction과 독립 스냅샷, 숨겨진 프리셋 승격, 실행 상태 전이, 삭제·사진 정리, 설정·초기화, 알림 계산과 푸시 작업 수명.
- 기존 검사와 별도로 위 세 시나리오를 실패하는 회귀 테스트로 재현했다. 테스트 코드와 임시 DB는 작업 트리 밖 복사본에만 만들었다.
- 브라우저에서 임시 DB로 직접 입력 일정 생성, 매개변수 태스크 추가, 메모 자동 저장, 태스크 완료, Today 진행률과 월간·일간 캘린더 반영을 확인했다.
- 실제 `data/` DB·사진·키는 테스트에 사용하지 않았다. 임시 서버와 브라우저는 종료했다.
