# 2026-09-27 트랙

## 변경

- 계정당 기본 포함 3개의 트랙 생성·목록·이름 변경·전환을 추가했다. 한도는 계정 정책 필드로 분리하고 동시에 생성해도 트랜잭션으로 지킨다.
- 하나의 SQLite 파일에서 계정/트랙 소속과 복합 FK·인덱스로 워크·태스크·태그·자동완성·연결·일정·실행·사진·초기화를 분리했다. 기존 ID·사진 경로·스냅샷을 기본 트랙에 보존하는 migration을 추가했다. 계정 단위 revision 쓰기를 트랙 revision으로 대체했다.
- 좌상단 타이틀 옆에 긴 이름 말줄임·키보드 선택이 가능한 전환기를 배치했다. 목록 폭을 별도 확보하고 모바일 스티커 진입은 아이콘으로 표시한다. 새 트랙은 메뉴에서 선택하며 삭제·이동·복사는 이번 범위가 아니다.
- 요청·동시 조회 공유·페이지 조회·메모 초안·스티커를 트랙별로 격리했다. 전환 전 메모 저장·진행 중 쓰기 확인과 입력 폐기 확인을 수행하며 실패하면 현재 입력을 유지한다. 앱 공통 설정과 모든 트랙 알림은 전환 바깥에 둔다. 알림 URL은 대상 트랙으로 이동한다.
- 기존 변경은 사용자 UI·다국어·스티커·성능 개선·문서 하네스 작업이다. 같은 파일의 기존 변경을 보존했다. 기존 테스트의 임의 소유자 이동 fixture는 새 소속 불변 조건에 맞게 타 계정 레코드를 직접 생성하도록 바꿨고, 역사적 migration 테스트는 현재 API 대신 과거 스키마를 직접 채워 이전을 검증한다. 기존 탐색 테스트에서 드러난 지연 기본 링크 탐색 경합은 앱이 hash 링크의 history와 reducer를 함께 갱신하도록 고쳤다.

## 문서

- SPEC·TRACKS: 트랙 범위, API, 호환 요청, 데이터 이전, 동시성, 알림 계약.
- STATUS·CODE_MAP·PRODUCT_GUIDE·README: 구현 범위·경로·사용법과 문서 진입점.
- DESIGN_SYSTEM: 헤더 공간 보장·반응형 규칙·선택 목록 폭. I18N: 세 언어 트랙 안내. WEB_PUSH: 앱 전체 알림과 트랙 목적 링크.
- TASK_CUSTOMIZATION은 태스크 매개변수 계약을 바꾸지 않아 수정하지 않았다. 기존 agent 하네스와 승인 정책은 변경하지 않았다.

## 검증

- `npm run check:frontend` 통과: 포맷·lint·디자인/구조 검사, 59개 파일 323개 테스트, TypeScript와 production build. 580kB JS 청크에 대한 Vite 권고 경고는 남아 있으며 빌드는 성공했다.
- `npm run check:backend` 최종 통과: fmt·경고 없는 clippy, 90개 테스트, build. 최종 SQL 검토에서 발견한 상세 종류 호환 INSERT 범위와 중복 인덱스 정리 후 전체 재실행도 통과했다.
- 최종 diff 검토와 `git diff --check` 통과. 변경 파일을 이 기록에 연결한 뒤 `npm run check:docs`로 문서 링크와 변경 기록 범위를 확인했다.
- 브라우저: 실제 앱의 트랙 생성·선택, 긴 이름과 목록 표시를 확인했다. 320/390px 모바일과 1280px 데스크톱에서 스케줄 추가 버튼과 겹치지 않는다. 검증 화면은 로컬 `test-results/tracks/header-desktop.png`에 저장했다.
- 서버 선택 검사: 트랙 분리·같은 이름·교차 FK·초기화·전체 트랙 리마인드/발송 대기열·동시 3개 제한·소유자 격리·증설·복합 인덱스 조회 계획 통과. 과거 스키마의 태그/연결/메모/실행 값/사진 메타데이터 이전과 foreign_key_check 통과.
- 개발 중 발견·수정: 직접 소유자를 이동하던 기존 fixture, 트랙 없는 옛 EXPLAIN 쿼리와 역사적 API fixture, TypeScript 헤더 타입/번역 키 구조, React lint의 인자 변경/render prop ref 전달. 메모의 동기 오류 후 재시도 잠금과 지연 링크 탐색도 회귀 검증으로 보완했다. 이 실패들은 이번 작업 중 발생했으며 기존 검사 합격으로 대체하지 않는다. 최종 검토에서 기본 트랙 호환 INSERT의 상세 종류 UPDATE를 NULL 소속 행에 한정하고 같은 이름의 다른 트랙 보존과 사진 교차 트랙 거부를 추가 검증했다.
- 프런트 선택 검사 최초 실행은 샌드박스 esbuild spawn EPERM으로 시작하지 못했다. 권한 확장 재실행을 사용했다. 최초 Vite 명령은 인자 전달 오류로 잘못된 포트에 떠 종료했고, 올바른 명령도 샌드박스 EPERM 후 권한 확장으로 실행했다.
- 성능: Node SQLite 메모리 DB, 일정 30,000개를 동일 계정/단일 트랙에 보관, 7회 반복 중앙값. 각 범위/개수 조회는 회차당 100번, 단일 UPDATE는 회차당 1,000번 수행했다. 최종 migration으로 재측정한 범위 100건 조회 4.546 → 4.460ms, 개수 조회 2.076 → 1.973ms, UPDATE 0.002319 → 0.001770ms. migration 165ms, FK 위반 0개. 이 합성 조건에서 큰 하락은 없었으며 실제 디스크·기기·네트워크의 보장은 아니다.
- 실제 데이터 폴더는 사용하지 않았다. 브라우저는 test-results 아래 별도 DB·사진 경로와 3007/15177 포트를 사용했다. 실제 외부 푸시 전달·공개 운영·원격 CI는 미검증이다.
