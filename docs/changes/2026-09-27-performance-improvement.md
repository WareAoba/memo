# 2026-09-27 실측 병목 성능 개선

## 변경

[성능 조사](2026-09-27-performance-audit.md)에서 확인한 반복 렌더·Intl 생성·순차 페이지 호출 비용을 개선했다. 작업 시작 시 기존 UI·스티커·일정 상태/조회·구조 감사 변경 142개 파일의 기록 게이트가 통과했다. 맡은 기존 파일의 전체 diff를 확인하고 보존했으며, 이번 작업은 아래 변경만 담당한다. 백엔드·실제 data·의존성은 변경하지 않았다.

- Today의 1초 시계 상태를 `TodayOverview`로 이동했다. 요약·다이얼은 기존 주기로 갱신하지만 상세 카드·실행 편집기는 시계 때문에 다시 렌더하지 않는다. 데이터 갱신·저장 잠금·선택·날짜 변경·실패 초안 보존은 Today에 유지한다. JSX 구조·스타일·완료/메모 동작은 그대로 옮겼다.
- `timeRange`에서 시간대별 날짜/시각 `Intl.DateTimeFormat`을 재사용한다. 최대 64개 시간대 쌍을 보관하고 가장 오래 삽입한 항목부터 제거한다. 시각·날짜 결과나 UTC offset은 캐시하지 않으므로 자정·DST·설정 시간대 변경을 매번 현재 instant로 계산한다. 내부 날짜 키/24시간 표기용 고정 locale이며 번역 문자열을 캐시하지 않는다.
- 일정 상세/요약의 날짜 범위 조회만 페이지 크기를 20→100으로 변경했다. 서버의 기존 상한 100을 사용하며 검색·일반 목록은 20을 유지한다. 순차 조회·revision 검증·최대 3회 전체 재시도·중복 방지·취소·진행 중 요청 공유는 유지했다.
- 새 라이브러리는 추가하지 않았다. 이번 병목은 React 상태 위치와 브라우저 기본 API 재사용으로 줄었다. TanStack Query의 완료 데이터 캐시, 페이지 병렬화, 가상 목록, React Compiler, 지연 로딩은 별도 변경으로 남긴다. 특히 Query는 현재의 완료 데이터 비캐시/쓰기 이후 갱신 계약을 먼저 설계해야 한다.

### 같은 조건의 변경 전후 측정

[원자료·기준 소스·측정 하네스](2026-09-27-performance-improvement-measurements.json). Windows Chrome 154, 3072×1594, CPU 제한 없음. 실제 Today/Calendar/API 모듈을 production Vite + React profiling renderer로 빌드하고 생성 데이터/fetch 대체만 사용했다. 실제 계정·DB를 사용하지 않았다. 동일 탭에서 변경 전/후 각 1회, 각 Today 조건 7.5초 중 초기 800ms를 제외한 7회 commit의 중앙값이다. React 렌더 시간이며 화면 paint·INP·LCP 측정은 아니다.

| Today 일정/태스크 | 이전 1초 갱신 | 개선 후 | 감소 |
| --- | ---: | ---: | ---: |
| 10 / 30 | 3.2ms | 1.0ms | 약 69% |
| 50 / 150 | 16.9ms | 2.5ms | 약 85% |
| 100 / 300 | 38.0ms | 5.7ms | 약 85% |

- 100개 조건의 가장 느린 steady commit: 46.3→7.2ms. DOM은 양쪽 8,601개로 동일하다. 최초 데이터 렌더는 88.0→82.2ms로 여전히 크므로 초기 렌더 병목까지 해소했다고 주장하지 않는다.
- `scheduleAppearance` 100회 계산 중앙값: 6.4→0.4ms(15회 중 초기 3회 제외). 이전 조사용 강제 formatter override는 비활성화했고 양쪽 실제 제품 함수를 사용했다. JSON의 `cachedFormatters:false`는 override 플래그이며 개선 후 제품 내 재사용을 끄는 의미가 아니다.
- 1,000개 요약 전체 조회: 50→10회. 요청당 40ms 지연을 흉내 낸 첫 조회 2,328.2→463.8ms, 즉시 재조회 2,345.1→466.9ms. **실제 네트워크/서버 지연 수치가 아니다.** 재조회도 새 요청을 보내는 기존 정책을 유지한다. 원자료의 totalCalls는 첫 조회+재조회 합계다.
- 100개 상세 Today 조회는 5→1회. 범위 조회 결과 순서와 반환 개수는 유지한다. 데이터 총량·DOM 수를 줄인 변경은 아니다.

## 문서

- SPEC: Today와 상세/요약 날짜 범위 페이지 크기 100 반영. 서버 API의 허용 범위와 검색 20개 계약은 유지한다.
- STATUS: 시계 렌더 경계·포맷터 재사용·범위 페이지 확대를 현재 구현으로 기록했다.
- CODE_MAP: TodayOverview, 렌더 격리 회귀, 시간대 변환/포맷터 경로를 안내한다. CHANGES에 이번 기록을 연결했다.
- PRODUCT_GUIDE·DESIGN_SYSTEM·I18N은 UX·CSS·번역 계약이 바뀌지 않아 추가 수정하지 않았다. 기존 변경과 과거 성능 조사 기록은 보존한다. 과거 조사의 문서 게이트 보류는 후속 구조 감사 작업에서 이미 연결되어 이번 시작 검사에서 통과했다.
- 측정 실행 파일·빌드·중간 결과는 무시된 test-results 아래에 두고, 재현에 필요한 하네스와 변경 전 제품 소스·변경 후 SHA-256·결과는 위 JSON에 보존했다.

## 검증

- 선택 회귀: API 페이지 조회·Today·TodayDial·scheduleAppearance·시간대·렌더 경계 6개 파일 53개 테스트 통과.
- 새 회귀: 100개+마지막 페이지, revision 충돌 후 전체 재조회, 1,000개 요약 10회 조회, 검색 20 유지, 시작/종료 시각 갱신 중 상세 렌더 미발생·미저장 초안 보존·타이머 정리, 자정·뉴욕 DST 시작/종료·45분 시간대·잘못된 시간대.
- 브라우저: 변경 전/후 동일 하네스 완료 및 결과 파일 수집. 측정 조건과 한계는 위 표 및 원자료에 기록했다.
- 중간 실행 제한: Vite/esbuild 및 Git 하위 프로세스가 샌드박스에서 EPERM으로 차단됐다. 승인된 권한 확장 재실행으로 선택 테스트와 측정 빌드가 통과했다. 제품 실패로 분류하지 않는다.
- 최종 `npm run check:frontend` 통과: 문서 링크 50개 Markdown/변경 150개 파일 기록, Prettier, ESLint/design, 구조 검사 3개 fixture/112개 모듈, 제품 테스트 57개 파일 314개, TypeScript, Vite production build. JS 570.68 kB/gzip 173.89 kB이며 기존 500 kB 청크 경고는 유지된다.
- 변경 전 소스와 이번 diff를 대조했고 `git diff --check` 통과(기존 CRLF 정규화 경고). 기록 명령이 이번 15개 파일만 연결한 것을 확인했다. 이 검사 결과 문장 갱신 후 기록과 문서 검사를 다시 실행한다. 측정용 탭과 localhost:15180 서버를 종료했다.
- 미검증: 실제 모바일 기기·운영 데이터·WAN, 전체 화면 paint/상호작용 지연, 원격 CI. 서버·migration·API 스키마는 변경하지 않아 백엔드 완료 검사를 재실행하지 않았다. 기존 번들 크기 경고와 큰 목록의 최초 렌더/DOM 비용은 남는다.
